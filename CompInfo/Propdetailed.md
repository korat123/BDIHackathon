### Idea 7: Patient Rescue Radar — LTFU Prediction

### เทคโนโลยีหลัก / อัลกอริทึม / โมเดล

ระบบรับ input เป็นข้อมูล EMR ผู้ป่วยเบาหวานจากโรงพยาบาล ประมวลผลผ่าน ML pipeline แล้วส่ง output เป็นรายชื่อผู้ป่วยเสี่ยง LTFU พร้อมเหตุผลที่อ่านเข้าใจได้ไปยัง Case Manager เพื่อติดต่อเชิงรุกก่อนที่ผู้ป่วยจะหายออกจากระบบจนเกิดภาวะฉุกเฉิน

ระบบเริ่มจากการอ่านข้อมูล EMR ของผู้ป่วยเบาหวาน (70,000+ คน) ที่จัดเก็บในรูปแบบ XLSX wide-format ซึ่งมีคอลัมน์มากกว่า 4,000 ช่อง โดยแต่ละช่องแทนค่าตรวจวัดในช่วงเวลา (period) ต่างๆ นับจากวันวินิจฉัย จากคอลัมน์ทั้งหมดนี้ ทีมสกัดออกมาเป็น feature เพียง 12 ตัวที่สรุป pattern ระยะยาวของผู้ป่วยแต่ละคน แทนที่จะส่งค่าทุก period เข้าโมเดลโดยตรงซึ่งจะทำให้โมเดลซับซ้อนเกินจำเป็น

สิ่งที่ทำให้แนวทางนี้ต่างออกไปคือวิธีที่ทีมมองข้อมูลที่ "หายไป" ในระบบ EMR ของโรงพยาบาล ถ้าผู้ป่วยไม่มาพบแพทย์ ก็จะไม่มีการบันทึกค่าใดๆ เลย ดังนั้นช่องว่างในข้อมูลจึงไม่ใช่ข้อมูลเสีย แต่คือสัญญาณที่บ่งบอกว่าผู้ป่วยคนนั้นกำลังเริ่มหายออกจากระบบ นักวิจัยด้าน clinical data science เรียก pattern แบบนี้ว่า Missing Not At Random (MNAR) และงานวิจัยจาก Sperrin et al. (JMIR 2021) และ Nijman et al. (JMIR 2025) ยืนยันว่าการนำ missingness indicators เข้าเป็น feature ช่วยเพิ่มประสิทธิภาพโมเดลได้อย่างมีนัยสำคัญใน clinical EMR data ทีมจึงไม่เติมค่าเฉลี่ยลงไปเพื่อซ่อน pattern นั้น แต่เปลี่ยน pattern ของการหายไปให้กลายเป็น feature แทน

จาก insight นี้ ทีมสร้าง feature หลักสามกลุ่มจากข้อมูล EMR ที่มีอยู่

- **พฤติกรรมการมาพบแพทย์** — ดูว่าผู้ป่วยมาสม่ำเสมอแค่ไหน เคยหายไปต่อเนื่องนานสุดกี่เดือน และข้อมูลล่าสุดอยู่ที่ period ไหน ตัวเลขเหล่านี้บอกได้ตรงๆ ว่าผู้ป่วยห่างหายมากน้อยแค่ไหนก่อนที่จะถูกนับว่า LTFU
- **แนวโน้มสุขภาพ** — ดูทิศทางของค่าความดันโลหิตและน้ำตาล HbA1c ข้ามเวลา ไม่ใช่แค่ค่าล่าสุด ผู้ป่วยที่ค่าแย่ลงต่อเนื่องแต่มาพบแพทย์น้อยลงเรื่อยๆ มีความเสี่ยงสูงมาก
- **ความสม่ำเสมอในการรับยา** — ถ้าผู้ป่วยหยุดรับยาในช่วงปลาย มักตามมาด้วยการหายออกจากระบบในไม่ช้า

ผู้ป่วยจะถูกนิยามว่า LTFU เมื่อขาดการบันทึก visit ต่อเนื่องอย่างน้อย 3 period (ประมาณ 6 เดือน) ซึ่งสอดคล้องกับ clinical consensus จากงานวิจัยในกลุ่มผู้ป่วย NCD

สำหรับโมเดล ทีมเลือก XGBoost ด้วยเหตุผลสามข้อ ข้อแรกคือรองรับข้อมูล missing ได้โดยตรงโดยไม่ต้องเติมค่าก่อน ซึ่งสำคัญมากในงานนี้เพราะถ้าเติมค่าเฉลี่ยลงไปก็จะทำลาย MNAR signal ที่เป็นหัวใจของระบบ ต่างจาก Random Forest ที่ทำงานกับ tabular data ได้ดีแต่ต้องการ imputation ล่วงหน้าก่อนเสมอ ข้อสองคือ XGBoost มี parameter ที่ช่วยปรับให้โมเดลให้น้ำหนักกับผู้ป่วย LTFU มากขึ้นตามสัดส่วนจริง เพราะในชุดข้อมูลจริงผู้ป่วย LTFU มักเป็นกลุ่มน้อยเมื่อเทียบกับ Active ถ้าไม่จัดการตรงนี้โมเดลจะเรียนรู้แค่การทำนาย Active ไว้ก่อนเสมอและประสิทธิภาพที่ได้จะหลอกตัวเอง ข้อสามคือ train เร็วพอสำหรับการแข่งขัน 2 วัน ต่างจาก Neural Network ที่ใช้เวลาหลายชั่วโมง

ประเมินผลโมเดลด้วย 5-fold cross-validation เพื่อให้มั่นใจว่าผลลัพธ์ไม่ได้เกิดจากความบังเอิญ และใช้ AUROC เป็นตัวชี้วัดหลักเพราะวัดความสามารถแยกแยะสองกลุ่มได้ตรงกว่า accuracy ธรรมดาในกรณีที่ข้อมูลไม่สมดุล งานวิจัยที่คล้ายกันในการทำนาย LTFU ของผู้ป่วย HIV ด้วย XGBoost ทำได้ AUROC 85.9%

ผลลัพธ์ที่โมเดลให้ออกมาไม่ใช่แค่คะแนนตัวเลข ทีมใช้ SHAP เพื่อแปลผลออกมาเป็น 3 เหตุผลที่ Case Manager เข้าใจได้ เช่น "ไม่มาพบแพทย์ต่อเนื่อง 14 เดือน" หรือ "ความดันครั้งล่าสุด 158 mmHg และไม่มีบันทึกการรับยา" เพื่อให้ผู้ใช้งานตัดสินใจได้จริงโดยไม่ต้องเชื่อ black box

เครื่องมือที่ใช้: Python, pandas, XGBoost, SHAP, scikit-learn, openpyxl, matplotlib

### แพลตฟอร์มและการ Deploy

สำหรับ Hackathon prototype ทีมพัฒนาใน Jupyter Notebook โดยเริ่มจากชุดข้อมูลตัวอย่าง 100 คน และจะ scale ขึ้นเป็น 70,000 คนเมื่อได้รับข้อมูลจริง output ของ prototype คือ risk score พร้อม SHAP summary plot และ patient risk card ต่อคน ตัวอย่างหน้าตาของ risk card ที่ Case Manager จะเห็น: "ผู้ป่วย DM-00142 | ความเสี่ยง LTFU: 87% | เหตุผล: (1) ไม่มาพบแพทย์ 14 เดือน (2) ไม่มีผล HbA1c ใน 2 ปี (3) ความดันล่าสุด 158 mmHg → แนะนำ: โทรติดต่อภายใน 7 วัน"

สำหรับการใช้งานจริงในโรงพยาบาล ทีมออกแบบให้ระบบดึงข้อมูลจาก HIS ของโรงพยาบาลอัตโนมัติทุกคืน ประมวลผลผ่าน FastAPI backend แล้วแสดงผลบน Streamlit dashboard ที่ Case Manager สามารถเปิดดูรายชื่อผู้ป่วยเรียงตามระดับความเสี่ยง พร้อม 3 เหตุผลหลักต่อคนได้ทันที FastAPI เลือกเพราะเป็น Python-native ทำให้ใช้ model pipeline เดิมได้โดยตรงโดยไม่ต้องแปลงภาษา ส่วน Streamlit เลือกเพราะสร้างได้เร็วภายใน hackathon และ medical staff ที่ไม่ถนัดด้าน tech สามารถใช้งานได้ทันทีโดยไม่ต้องฝึกพิเศษ

เลือก deploy แบบ on-premise ที่โรงพยาบาลโดยตรง เพื่อให้ข้อมูลผู้ป่วยไม่ต้องออกไปยัง cloud ภายนอก ซึ่งสอดคล้องกับ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA) ระบบส่งออกเพียง risk score และเหตุผล 3 ข้อ ไม่มีการส่งข้อมูลทางการแพทย์ดิบออกภายนอกใดๆ นอกจากนี้ก่อน deploy ทีมจะตรวจสอบว่าโมเดลไม่ bias ต่อกลุ่มผู้ป่วยใดเป็นพิเศษ โดยวิเคราะห์ AUROC แยกตาม age group และ DM subtype เพื่อให้ระบบทำงานได้เป็นธรรมกับผู้ป่วยทุกกลุ่ม
